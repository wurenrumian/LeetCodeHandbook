## 二、P0 错误（会教出错误解法，必须改）

### P0-1 `sliding-window/3-longest-substring.md:182` —— 断言 `if` 够用，实际会把答案算大

原文：

> ### `while` 而不是 `if`
> `if` 够不够？在这题里**恰好够**，因为每轮最多踢掉一次让条件重归合法。

这句话是错的，而且是本题最典型的错误认知。

**实测**（用页面自己的用例）：

| 输入 | 正确（`while`） | 改成 `if` | |
|---|---|---|---|
| `"pwwkew"` | 3 | **4** | 错 |
| `"abba"` | 2 | **3** | 错 |
| `"tmmzuxt"` | 5 | **6** | 错 |
| `"abbab"` | 2 | **3** | 错 |

原因：加入 `s[right]` 后 `count[s[right]]` 最多是 2，但要把它降回 1，**可能需要从左边连续踢掉好几个字符**。`"pwwkew"` 读到第二个 `w` 时窗口是 `[p,w,w]`，踢掉 `p` 之后 `count[w]` 仍是 2 —— `if` 只收缩一次就收手，窗口还非法，`best = right-left+1 = 4` 就上去了。

**建议改法**：

> `if` 在这题**不够**。举 `"pwwkew"`：读到第二个 `w` 时窗口是 `[p,w,w]`，踢掉 `p` 之后 `count[w]` 还是 2 —— 一次收缩修不好，必须 `while`。
> 真正能用 `if` 的是**定长窗口**（643、438）：长度固定时每轮进出各一个元素，条件不可能连续违反。

注：同页 :184–187 的"定长用 `if`、变长用 `while`"这条总结是对的，只是被前面那句"恰好够"抵消了。**改掉那半句即可。**

### P0-2 `stack/20-valid-parentheses.md:252` —— 括号生成的条件写错

原文（变体表最后一行）：

> 给出所有合法组合（22 括号生成） | 不再是判定，改成回溯：记录 `used_left` / `used_right`，只在 `used_right <= used_left` 时放右括号

正确条件应是 **`used_right < used_left`**。写成 `<=` 会允许左右数量相等时继续放右括号，于是生成大量以 `)` 开头的非法串。

**实测**（穷举并校验每个输出是否合法）：

| n | `right < left` | `right <= left` |
|---|---|---|
| 1 | 1 个，全合法 | 2 个，**1 个非法** |
| 2 | 2 个，全合法 | 5 个，**3 个非法**（`))(`、`)((`、`)()(`） |
| 3 | 5 个，全合法 | 14 个，**9 个非法** |

**建议改法**：`used_right <= used_left` → `used_right < used_left`，并补一句"右括号数以**严格小于**左括号数为前提，否则会生成以 `)` 开头的串"。

## 三、P1 缺陷（讲错、自相矛盾、断言失效）

### P1-1 `two-pointers/26-remove-duplicates.md:108`、`:252` —— 80 题"只改一个数字"不成立

原文 :108：

> 只改一个数字：比较对象从 `nums[slow - 1]` 变成 `nums[slow - 2]`，同时 `slow` 从 2 起步。

这句话自己就列了**两**处改动（比较对象 + 起点），却称"只改一个数字"。更要紧的是：**照这个配方写，`n < 2` 时返回错值**。

按页面配方实现后实测：

| 输入 | 返回 | 正确 |
|---|---|---|
| `[1]` | **2** | 1 |
| `[]` | **2** | 0 |
| `[1,1]` | 2 | 2 |
| `[1,1,2,2,3]` | 5 | 5 |

因为 `slow = 2` 起步、`fast` 也从 2 开始，长度 ≤ 2 时循环一次都不进，直接返回 2。

26 题页面在 :234 反复强调"必须先特判空数组"，而这个 80 的变体**恰好把这个特判弄丢了**——它是最容易被复制粘贴踩到的坑。

**建议改法**：:108 改为

> 需要改三处：比较对象换 `nums[slow - 2]`、`slow` 从 2 起步、**并补上 `if (n <= 2) return n;`**（否则 `[1]` 会返回 2）。

:252 表格同步补"＋长度特判"。另外"保留 k 个"的通用形式 `slow - k` 同样需要 `if (n <= k) return n;`，这句值得写进去，因为它是这个家族**唯一**的边界陷阱。

### P1-2 `dp/322-coin-change.md:96` —— "`min` 恰好不会选中它"说反了

原文：

> 虽然实际大多变成 `INT_MIN`，`min` 恰好不会选中它，但这是运气不是设计。

**实测**：`INT_MAX + 1` 溢出得 `INT_MIN`，而 `min(INT_MAX, INT_MIN) == INT_MIN` —— `min` **一定**会选中溢出值。带这个 bug 的代码返回的是 `INT_MIN` 而不是 `-1`：

```
coins = {2}, amount = 3  →  返回 -2147483648（应为 -1）
```

这句话的危险在于它暗示"用 `INT_MAX` 虽然 UB，但 `min` 不选它，结果碰巧还是对的"，会让人以为问题实战无害。而同一页 :98–101 的 `danger` 块说的是"这是 UB，OJ 上偶发 RE"，两处口径矛盾。

**建议改法**：

> 溢出后通常变成 `INT_MIN`，而 `min` **一定会选中它**（`INT_MIN < INT_MAX`），于是 `dp[i]` 被污染成负数，最终返回一个荒谬的值而不是 `-1`。这不是"碰巧没事"，是"碰巧看起来像个数字"。

### P1-5 `binary-search/34-first-last-position.md:217–219` —— 警告与本页代码自相矛盾

原文：

> **如果你把 `last` 的计算挪到命中判断之前，这个保证就没了。** 顺序敏感的代码，别为了"看起来先算完再判断"而重排。

但本页 :110–115 的代码**本来就是先算 `last` 再判断**：

```cpp
int first = bound(nums, target, true);
int last  = bound(nums, target, false) - 1;               // ← 先算
if (first == (int)nums.size() || nums[first] != target)   // ← 后判
    return {-1, -1};
```

**实测确认这样写无害**：取 `nums = {5,7,8,10}, target = 100`，得 `first = 4`（越界）、`last = 3`（合法但错误的下标），但 `first == size` 成立，仍正确返回 `{-1,-1}`。`last` 在早退分支里根本没被使用。

这条警告既不符合事实，也与本页代码相反，是凭空造出的"顺序敏感性"。

**建议**：删掉该 `warning` 块；或换成真正成立的说法：

> `last` 可以先算，因为它只在命中确认后才被**使用**。真正不能颠倒的是 :115 的两个条件本身 —— 必须先判越界、再取 `nums[first]`。

### P1-6 `sliding-window/3-longest-substring.md:225` —— 给出的两个"修法"都不安全

原文（坑点 3）：

> 用 `static_cast<unsigned char>(s[right])` 或直接 `int(s[right]) & 0x7F`。

两个都有问题：

1. **`& 0x7F` 会把不同字节映射到同一格**：`0xC3 & 0x7F == 67`，而 `'C' == 0x43 == 67`。两个毫不相干的字符被当成同一个，判重直接失效 —— 比越界更隐蔽。
2. **`static_cast<unsigned char>` 配 `array<int,128>` 仍然越界**：`unsigned char` 范围 0–255，`0xE4`（汉字首字节）是 228 ≥ 128，照样 UB。

**建议改法**：

> 桶扩到 256：`array<int, 256> window{};`，用 `++window[static_cast<unsigned char>(s[right])];`。
> **不要**用 `& 0x7F` —— 它把 `0xC3` 和 `'C'` 都映射成 67，不同字符被当成同一个，比越界更难查。

### P2-2 `two-pointers/index.md:89` —— "移动零不能交换"是错的

> 有效元素 = "非零"。本质和 27 题一样，但要保持相对顺序，因此**不能交换**，只能覆盖式写入。

`swap` 版完全正确，且同样保序：

```cpp
int slow = 0;
for (int fast = 0; fast < n; ++fast)
    if (nums[fast] != 0) swap(nums[slow++], nums[fast]);
```

实测 `[0,1,0,3,12]` → `[1,3,12,0,0]`、`[0,0,1]` → `[1,0,0]`，全部正确。交换之所以保序，是因为 `slow` 永远落在第一个 0 上，被换出去的恰好是 0（或 `slow == fast` 时换自己）。

**建议**：改为"**交换和覆盖都对**；覆盖式末尾要手动补零，交换式不用补但多一次写 —— 两种都保序"。

### P2-3 `hash-table/1-two-sum.md:216` —— 语义表说"最早的下标"，实际存的是最新

> `seen` | 「值 → **最早**的下标」，**只含已遍历部分**

:134 是 `seen[nums[i]] = i;` 无条件覆盖，同值重复出现时存的是**最新**下标。反例：`nums = {3,3,4}, target = 7`，轮到 `i=2` 时 `seen[3]` 已被 `i=1` 覆盖成 `1`，返回 `{1,2}` 而不是 `{0,2}`（实测确认）。

而 :273「重复元素为什么可以覆盖下标」明确讲了覆盖 —— 两处口径不一致。

**建议**：改成「值 → **最近一次**出现的下标」，并说明"因为先查后插，命中的必然是更早的那个，所以覆盖不影响正确性"。

### P2-7 `backtracking/78-subsets.md:263` —— "去重后是 8 个"需要额外的归一化

实测：16 条路径；直接 `set<vector<int>>` 去重仍是 **16**（`[1,2]` 与 `[2,1]` 是不同的 vector）；**把每个子集排序后**再去重才是 **8**。

### P2-8 `sliding-window/3-longest-substring.md:147` —— 回退时机归因错位

> `"abba"`：……遇到第二个 `b` 后 `left` 会**退回**到 `b` 的位置

实测逐步：

```
r=0 'a' → left=0
r=1 'b' → left=0
r=2 'b' → left=2      ← 前进，不是退回
r=3 'a' → left=1      ← 这里才退（2 → 1），best 被算成 3
```

真正的倒退发生在**下一个字符 `a`**，不是第二个 `b`。:215 的"会在第 4 个字符时把 left 从 2 退回 1"是准确的，:147 与之不一致。

**建议**：:147 改为"遇到第二个 `b` 时 `left` 被推到 2，**紧接着**读到的 `a` 会把它拉回 1"。
