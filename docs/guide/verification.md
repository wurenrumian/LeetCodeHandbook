# 验证与可信度

这个站点承诺两件事：**代码都能跑**、**同一件事全站只有一种写法**。承诺必须能被机器检查，否则它只是口气。

这一页说明：检查了什么、怎么检查的、以及检查不出来的部分。

## 三道门禁

改完任何内容，三条命令都要过：

| 命令 | 检查什么 | 不过会怎样 |
|---|---|---|
| `npm run verify` | 抽出所有带 `main` 的 cpp 代码块，逐个编译运行；`assert` 失败或编译报错就非零退出 | 一篇文档就能悄悄带进一段编译不过的示例 |
| `npm run check` | 注册四向一致、9 段结构、禁用单字母名、术语变体、三要素表 | 加一题忘了改侧边栏或题数，读者看到两个不同的站 |
| `npm run build` | VitePress 构建，死链、容器语法、组件错误都在这一步炸 | 页面在本地能看，上线 404 |

三条都靠**本地手动跑**，没有 CI：这个仓库是单人维护的文档库，门禁的价值在于"改完立刻知道哪里漏了"，不在于"拦住别人的 merge"。所以它们是三个 `npm` 命令，写进加题清单，靠习惯而不是靠平台。

其中 `npm run check` 的四类检查是：

1. **注册一致** —— `problems.ts`、侧边栏、专题总览的题数、实际 md 文件，四处必须指向同一批题；页头难度也要和注册表一致。
2. **结构一致** —— 每道题页必须有 `ProblemMeta`、速查卡、以及七个固定小节且顺序正确；页头题号和文件名要一致。
3. **命名一致** —— cpp 代码块里不许出现 `l` `r` `m` `c` `q` 这类单字母名，报错带文件行号。
4. **术语与三要素** —— 正文里出现术语表的"禁止写法"就报错；同专题各题的三要素表必须用同一批要素名。

## 两轮独立查验

除了机器门禁，这个站点做过两轮独立人工查验，报告原文在仓库根目录的 `review/`：

| 报告 | 查什么 | 结论 |
|---|---|---|
| A · 内容正确性 | 用**独立参考实现做随机差分测试**（约 48.7 万组用例）验证全部 16 段代码；逐个核对讲解文字 | 代码零缺陷；讲解查出 2 个 P0 + 7 个 P1 + 9 个 P2，已全部修复 |
| B · 工程与排版 | 自建**裸静态服务器**（不靠 `vitepress preview`）验路由与链接；移动端表格、标签、容器结构 | 查出 1 个 P0（无扩展名链接依赖 nginx rewrite）、移动端表格溢出最深 107px、标签漂移 12 处，已全部修复并复测 |

两份报告分开的原因很实际：A 查不出"移动端表格把整页顶出去"，B 查不出"`if` 恰好够用"这句话是错的。一个人同时查算法和 CSS，两边都会变浅。

## 这里查不出什么

诚实地说，上面这些只能证明**技术正确性**：

- 讲解是否真的好懂 —— 需要真实读者反馈
- 题目选得好不好 —— 是不是该讲的没讲、不该讲的占篇幅
- 内容对该读者的实际价值

这些只能靠人读一遍。

## 加一道新题的最低要求

1. 代码能过 `npm run verify`（带 `main`、断言覆盖边界）
2. 9 段结构齐全，`npm run check` 不报结构问题
3. 命名遵守 [术语表](/guide/glossary) 与 [写作约定](/guide/conventions) 的命名表
4. 三要素表的要素名和同专题其他页完全一致
5. 注册四处同步（`problems.ts`、侧边栏、专题总览题数、md 文件）

第 5 条看起来最琐碎，但它正是这个站点最容易悄悄变形的地方——数字型的冗余不会自己报警，所以由脚本盯着。
