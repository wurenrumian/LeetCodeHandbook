# 哈希表 · 用空间换查找

哈希表本身不是「算法」，它只做一件事：

> **把「这个键我见过吗」从一次 O(n) 的扫描，压成平均 O(1) 的一次计算。**

代价是先花 O(n) 空间把它们存下来。所以判断要不要用哈希，标准不是题目看着难不难，而是**你是不是在反复回答同一个查找问题**。

## 它替代掉的是什么

拿两数之和的暴力写法开刀：固定 `i`，再扫一遍 `j`。

```cpp
// O(n²)：对每个 i 都重新扫一遍剩下的元素
for (int i = 0; i < n; ++i)
    for (int j = i + 1; j < n; ++j)
        if (nums[i] + nums[j] == target)
            return {i, j};
```

内层那个 `j` 循环，每一轮都在回答同一个问题——「`target - nums[i]` 出现过吗」。这个问题和 `i` 的值无关，但被重新算了 n 次。

哈希表把「之前见过的所有值」预先存好，`j` 那一层就消失了。**O(n²) → O(n) 的全部来源就是这一个替换，没有别的技巧。**

一句话记法：

- 内层循环在**查表**（某个值在不在）→ 换哈希表
- 内层循环在**比大小**（谁大谁小、相邻关系）→ 想想排序或二分

## 什么时候该用

| 信号 | 例子 |
|---|---|
| 要记住「见过的值」 | 两数之和：记住 `nums[0..i-1]` |
| 要按某个特征分组 | 字母异位词：按排序后的串分组 |
| 要 O(1) 判存在 | BFS 的 `visited`、数组去重、出现次数 |
| 要「第一次出现的位置」 | 最长无重复子串、只出现一次的数字 |

反过来，这三种情况别急着上哈希：

- **要利用大小关系**：排序，哈希不保存顺序
- **要「连续的一段」**：滑动窗口，哈希只负责判断窗口内的状态
- **键是小范围整数**：直接用数组，比任何哈希都快

## 四种容器怎么选

| 容器 | 有序 | 单次查找 | 常数开销 | 什么时候用 |
|---|---|---|---|---|
| `array` / `vector` | 下标有序 | O(1) | 最小 | 键是 `0..255` 或 `0..n` 这类小整数 |
| `unordered_map` | 否 | 平均 O(1)，最坏 O(n) | 中：哈希 + 桶 + 节点 | 键是任意类型，只关心查得快 |
| `map` | 是，按 key 升序 | O(log n) | 大：每个节点都是红黑树结点 | 要按 key 顺序遍历，或找前驱后继 |
| `unordered_set` | 否 | 平均 O(1) | 中 | 只关心在不在，不关心值 |

### 数组是最快的哈希表

键的范围能确定时，数组严格优于 `unordered_map`：没有哈希函数、没有指针追逐、没有 rehash，还天然缓存友好。

```cpp
array<int, 26> count{};              // 统计小写字母，全部初始化为 0
for (char ch : str) ++count[ch - 'a'];
```

`unordered_map<char, int>` 能做同样的事，但每次访问都要算哈希、追指针、可能触发 rehash。同样统计 1000 个字符 2000 遍，`-O2` 下 `array` 版约 0.7ms，`unordered_map` 版约 5.4ms——**七到八倍的差距，而且这只是读**。**看到「只含小写字母」「ASCII 字符」「数字范围 `0..n`」，先想数组。**

### `map` 什么时候才值得

只有三种情况：

1. 输出要求**按 key 字典序**（例如结果要稳定可比较）
2. 需要 `lower_bound` / `upper_bound` 这类**有序查询**
3. 不能接受最坏 O(n)——需要 **O(log n) 的硬保证**

其余场景用 `map` 都是白白多付一个 log。

::: warning 哈希攻击
`unordered_map` 的平均 O(1) 有前提：哈希函数把键均匀散开。如果能构造大量落进同一个桶的键，查找就退化成 O(n)，整个算法回到 O(n²)。

标准库实现做了些缓解（libstdc++ 用质数桶数，字符串哈希额外做位混合；libc++ 用 2 的幂），但任何实现都无法完全排除刻意构造的冲突。OJ 上遇到「哈希解法莫名 TLE、换成 sort 反而过」，先怀疑这个，而不是怀疑自己写错了。日常面试和本地开发基本不用管。
:::

## 核心模式一：边遍历边记录

模板只有两行真代码，顺序是**先查、后插**：

```cpp
unordered_map<int, int> seen;       // 值 → 下标
for (int i = 0; i < n; ++i) {
    // 问：配合我的那个数，前面出现过吗
    if (seen.count(target - nums[i])) return answer;
    // 答完才把自己记下来
    seen[nums[i]] = i;
}
```

这两行的顺序决定了三件事：

1. **同一元素不会用两次**。反了的话，`nums = [3], target = 6` 会返回 `{0, 0}`。
2. **每个下标对只被考虑一次**。`seen` 里永远只有 `i` 之前的元素，所以 `(i, j)` 和 `(j, i)` 不会重复。
3. **一趟就够**。不需要先建表再查表，因为「查」只需要历史信息，「插」只需要当前信息。

::: info 循环不变式
进入第 `i` 轮时，`seen` 恰好是 `nums[0..i-1]` 的「值 → 下标」映射。整个算法就是维护这条不变式。
:::

## 核心模式二：构造归一化的 key

分组类问题（49 字母异位词、按字符集合分组）的共同点：**两个元素「等价」，但长得不一样**。哈希表只会比较 key 是否相等，所以第一步是把「等价」翻译成「key 相等」。

做法是给每个元素算一个**签名**，签名相同就进同一组：

| 题目 | 「等价」的定义 | 签名 |
|---|---|---|
| [49 字母异位词分组](/topics/hash-table/49-group-anagrams) | 字符多重集相同 | 排序后的串，或 26 位计数编码 |
| 242 有效的字母异位词 | 同上 | 两个计数数组相减是否全 0 |
| [1 两数之和](/topics/hash-table/1-two-sum) | 互补：`a + b == target` | 补数 `target - a` |
| 128 最长连续序列 | 相差 1 | 只从「没有前驱」的数起跳 |

**签名的构造方式直接决定复杂度**：排序签名 O(k log k)，计数签名 O(k + 26)。49 题把这两种并排测了速，结论是**短串（`k < 15`）排序更快，长串计数更快**。

::: tip 归一化比哈希表更重要
很多「哈希表题」真正的难点不在容器，在**你怎么定义等价**。想不出签名，`unordered_map` 也救不了你；想得出签名，连 `map` 都能过。
:::

## 坑点汇总

::: warning 坑点
1. **`operator[]` 会静默插入**。`seen[key]` 在 key 不存在时先插入 `value()`（int 就是 0），再返回引用。`if (seen[key])` 会一边查一边把表撑大，而且值恰好为 0 时判断直接错。只查不插，用 `count()` / `find()` / `at()`。

2. **遍历中修改容器 = 未定义行为**。`for (auto& kv : seen) seen[kv.first + 1] = 1;` 一旦触发 rehash，当前迭代器全部失效。要改就先收集 key，循环结束后再插。

3. **rehash 让迭代器失效，但不让元素引用失效**。`auto& group = groups[key];` 之后插入别的 key 触发了 rehash，`group` 仍然有效——`unordered_map` 的元素是独立节点，rehash 只重挂桶链表，节点不搬家。这一点和 `vector` 正好相反，别记混。

4. **`unordered_map` 不能直接拿 `pair` / `vector` 当 key**。标准库只为整型、浮点、字符串、`string_view` 等提供了 `std::hash` 特化，`pair` 和容器都没有。要么自己写 hash（并保证相等的 key 哈希相同），要么先序列化成 `string`。

5. **遍历顺序不稳定**。同一份代码在不同标准库、不同数据下，`unordered_map` 的遍历顺序都可能不同。题目说「任意顺序」才能直接返回；要求字典序就换 `map` 或最后排序。
:::

## 和别的专题怎么分界线

| 你的直觉 | 该去 |
|---|---|
| 「这个数以前出现过吗」 | 本专题 |
| 「哪一段的和等于 k」 | 前缀和 + 本专题（`sum → 最早下标`） |
| 「最长的不重复子串」 | [滑动窗口](/topics/sliding-window/)，窗口内部用哈希计数 |
| 「两数之和但数组已排序」 | [双指针](/topics/two-pointers/)，O(1) 空间更优 |
| 「分组后每组要按字典序输出」 | 本专题的 `map` 版本 |

## 变体索引

### 变体 1：边遍历边记录（[1 两数之和](/topics/hash-table/1-two-sum)）

一趟遍历，`seen` 存「值 → 下标」，重点在**先查后插**和 `count()` 与 `[]` 的区别。

**信号**：求和 / 求差等于定值，且要返回原下标。

### 变体 2：归一化 key 后分组（[49 字母异位词分组](/topics/hash-table/49-group-anagrams)）

一次遍历，`groups[key].push_back(str)`，重点在**签名怎么造**。

**信号**：把一堆东西按「某种意义下相同」分类。

### 变体 3：前缀和 + 哈希

把「子数组和等于 k」翻译成「`prefix[j] - k` 在之前出现过吗」，于是又回到模式一。这是哈希表在数组题里最高频的用法，`map` 存的是 `前缀和 → 出现次数`。

## 自检清单

写完任何一道哈希题，用这四个问题过一遍：

- 表里存的是**值**还是**下标**？返回类型需要哪个？
- 插入发生在查询**之前**还是**之后**？这决定了同一元素能不能被用两次。
- 「不存在」时读表会不会**插入垃圾**？有没有用到 `[]`？
- 循环里有没有**边遍历边插入**？
